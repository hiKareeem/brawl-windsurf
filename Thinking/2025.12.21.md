# Workstream A — Economy + Shop Scaffolding v0 (Server-Auth, Replicated)

## Objective
Create the minimum server-authoritative economy + shop scaffolding so we can:
- generate and replicate a shop offer list per player
- spend gold and buy XP
- emit the required Economy events

This workstream is intentionally **scaffolding-first** (design knobs, replication, server validation, and event emission), not full TFT economy.

## Constraints
- Dedicated-server authoritative; clients only send requests.
- Any randomness (shop offers) must be **server-only**, seeded, and auditable (may start deterministic for v0).
- Do not store economy state inside GAS.
- Follow module boundaries:
  - Add a `BrawlEconomy` module (per directory map) for economy systems.
  - `ABrawlPlayerState` owns economy/shop/progression/traits components.

## Files
- Add (new module):
  - `Source/BrawlEconomy/*` (Build.cs + module cpp/h)

- Add (components, minimum):
  - `Source/BrawlEconomy/Public/Components/BrawlEconomyComponent.h`
  - `Source/BrawlEconomy/Private/Components/BrawlEconomyComponent.cpp`
  - `Source/BrawlEconomy/Public/Components/BrawlProgressionComponent.h`
  - `Source/BrawlEconomy/Private/Components/BrawlProgressionComponent.cpp`
  - `Source/BrawlEconomy/Public/Components/BrawlShopComponent.h`
  - `Source/BrawlEconomy/Private/Components/BrawlShopComponent.cpp`

- Update:
  - `Source/BrawlMatch/Public/Game/BrawlPlayerState.h`
  - `Source/BrawlMatch/Private/Game/BrawlPlayerState.cpp`
  - `Source/BrawlMatch/Public/Game/BrawlPlayerController.h`
  - `Source/BrawlMatch/Private/Game/BrawlPlayerController.cpp`

## Tasks
1) **Economy state (Gold)**
   - Add `UBrawlEconomyComponent` to `ABrawlPlayerState`.
   - Replicate `Gold` (owner-only for now).
   - Server-only mutation APIs:
     - `bool CanAfford(int32 Cost) const`
     - `bool TrySpendGold(int32 Cost)`
     - `void AddGold(int32 Amount)`

2) **Progression state (XP/Level)**
   - Add `UBrawlProgressionComponent` to `ABrawlPlayerState`.
   - Replicate `XP` + `Level` (owner-only for now).
   - Implement a minimal `ServerBuyXP` path:
     - RPC on `ABrawlPlayerController` (request)
     - validate phase (Planning-like only)
     - validate gold
     - spend gold, apply XP, update Level
     - emit `Economy.BuyXP` with `Cost`, `XPGained`, `NewLevel`

3) **Shop offers replication (deterministic v0)**
   - Add `UBrawlShopComponent` to `ABrawlPlayerState`.
   - Replicate an offers list (FastArray recommended).
   - Provide server-only APIs:
     - `ServerRollOffers()` (deterministic at first: e.g., fixed list of `UnitDataId`s)
     - `ServerRerollOffers()` (spend gold, generate new offers)
   - Emit `Economy.Reroll` (including `ResultingOfferIds`).

4) **RPC surface (requests only)**
   - Add request RPCs on `ABrawlPlayerController` (names can be adjusted):
     - `ServerRequestBuyXP()`
     - `ServerRequestShopReroll()`
   - Rate-limit minimally and validate phase tags on the server.

## Acceptance Criteria
- Gold/XP/Level replicate correctly to the owning client.
- Shop offers replicate correctly to the owning client.
- `Economy.BuyXP` and `Economy.Reroll` are emitted on server commit.
- No client-authored economy state.

## Rules Applied
- brawl-implementation.md (server authority; seeded RNG policy)
- brawl-replication-contract.md (PlayerState economy replication)
- brawl-event-log-schema.md (required Economy event types)
- brawl-directories.md (BrawlEconomy module ownership)

# Workstream B — Roster Ownership Model v0 (PlayerState owns roster refs)

## Objective
Define and implement the authoritative “units I own” roster model (IDs + type refs) so Economy/Shop can create/sell/combine units without putting that state into GAS.

## Constraints
- Server owns the roster; clients are observers.
- Use stable server-issued `FBrawlUnitInstanceId`.
- Do not encode roster state in GameplayEffects/GameplayTags.

## Files
- Update:
  - `Source/BrawlMatch/Public/Game/BrawlPlayerState.h`
  - `Source/BrawlMatch/Private/Game/BrawlPlayerState.cpp`

- (Optional helper types in BrawlCore if needed):
  - `Source/BrawlCore/Public/Types/*` (only if a shared struct is needed)

## Tasks
1) **Replicated roster list on PlayerState**
   - Add a replicated roster list of owned units (owner-only initially).
   - Each entry should include at minimum:
     - `FBrawlUnitInstanceId UnitId`
     - `FPrimaryAssetId UnitDataId` (type identity for UI/shop)
     - optional: `int32 StarLevel` snapshot (if useful)
   - Use a FastArray if you expect frequent churn.

2) **Authoritative add/remove APIs (server-only)**
   - Provide `ServerAddUnitToRoster(UnitId, UnitDataId)` and `ServerRemoveUnitFromRoster(UnitId)`.
   - Unit actor lifetime remains separate (roster may outlive the actor in edge cases, but should be kept consistent).

3) **Bench capacity integration (hook point only for v0)**
   - Define where “bench full” is checked for purchases:
     - authoritative source is board occupancy (`ABrawlBoardActor`), not transforms.
   - For now, it is acceptable to stub the capacity check until purchase spawning is implemented.

## Acceptance Criteria
- PlayerState can replicate a stable roster list that UI can display.
- Roster is server-authored and uses stable unit IDs.

## Rules Applied
- brawl-implementation.md (stable IDs; keep economy state out of GAS)
- brawl-replication-contract.md (PlayerState roster refs replicate)

# Workstream C — StarLevel Guard + Combine Deferral (Combat vs Bench)

## Objective
Enforce the rule:
- **Never resolve a StarLevel upgrade** for a unit that is actively fighting on the **field** during `Phase.Combat`.
- Bench units may still combine anytime.
- Combines involving a unit in combat resolve at start of next `Phase.Planning`.

## Constraints
- Must not violate module boundaries:
  - Use `IBrawlMatchContextInterface` (BrawlCore) to read phase.
  - Use `IBrawlGridOccupantInterface` (BrawlCore) grid snapshot to know bench vs field.
  - Do not make `BrawlUnit` depend on `BrawlMatch` concrete types.

## Files
- Update:
  - `Source/BrawlUnit/Public/Actors/BrawlUnitCharacter.h`
  - `Source/BrawlUnit/Private/Actors/BrawlUnitCharacter.cpp`
  - `Source/BrawlGrid/Private/Actors/BrawlBoardActor.cpp`

- Add (if not already present):
  - `Source/BrawlUnit/Public/Components/BrawlStarCombineComponent.h`
  - `Source/BrawlUnit/Private/Components/BrawlStarCombineComponent.cpp`

## Tasks
1) **Bench/field snapshot on units**
   - Implement `IBrawlGridOccupantInterface` on `ABrawlUnitCharacter` with a server-authored `FBrawlGridCoordSnapshot`.
   - The board (authoritative occupancy owner) updates this snapshot when it teleports/moves a unit actor.

2) **Guarded upgrade path (combine resolver, not raw SetStarLevel)**
   - Do **not** globally block `SetStarLevel(...)` (to avoid interfering with init/tests).
   - Instead, in the combine-resolution code path:
     - Resolve current phase via `IBrawlMatchContextInterface`.
     - Determine whether the target unit is on bench via `IBrawlGridOccupantInterface`.
     - If `Phase.Combat` AND `bIsBench == false`:
       - do not apply the upgrade now
       - store a pending upgrade record (UnitId → DesiredStarLevel)
     - Else:
       - apply immediately

3) **Resolve pending upgrades at Planning start**
   - At the start of `Phase.Planning`, apply pending upgrades deterministically.
   - Clear the pending list only after successful application.

## Acceptance Criteria
- A unit on the field during combat never upgrades star level immediately.
- The same combine succeeds immediately for bench units.
- Deferred upgrades apply when planning starts.

## Rules Applied
- brawl-implementation.md (star combine guard rule; server authority)
- brawl-gameplay-tags-contract.md (Phase.* ownership)
- brawl-directories.md (module boundaries)
