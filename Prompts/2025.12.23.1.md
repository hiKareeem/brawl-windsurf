# Priority / sequencing recommendation (includes BrawlUI)

## Recommendation
Promote **BrawlUI** from backlog 6 to **Workstream B**, scoped as a **read-only debug overlay** built on MVVM ViewModels.

Why this makes sense now:
- The project already replicates enough authoritative state to make a UI useful immediately:
	- `ABrawlGameState` phase + time remaining
	- `ABrawlPlayerState` roster + shop offers + trait counts
	- `ABrawlBoardActor` occupancy for bench/field visualization
- A debug overlay reduces iteration time for:
	- placement validation
	- shop/traits sanity checks
	- combat event verification in LVL_Sandbox

Guardrails:
- BrawlUI must not contain gameplay rules.
- Gameplay modules must not depend on `BrawlUI`.
- The overlay should be optional/dev-oriented and safe to disable.

**Rules Applied:** `rules/brawl-directories-2.md` (“Module: BrawlUI”), `rules/brawl-implementation.md` (module boundaries), `rules/brawl-replication-contract.md` (replicated state is canonical)

# Workstream B — BrawlUI v0 (MVVM ViewModels + Debug Overlay)

## Objective
Create a minimal `BrawlUI` module and a debug/testing overlay widget that binds to ViewModels and displays live match state.

## Rules / constraints
- UI is presentation-only: no server validation, no gameplay mutation.
- Prefer binding to replicated state rather than “scraping” actor transforms.
- No new dependencies from gameplay modules to `BrawlUI`.

## Primary references
- Planned module + ViewModel names:
	- `rules/brawl-directories-2.md` (“Module: BrawlUI”)
- State sources:
	- `Source/BrawlMatch/Public/Game/BrawlGameState.h`
	- `Source/BrawlMatch/Public/Game/BrawlPlayerState.h`
	- `Source/BrawlGrid/Public/Actors/BrawlBoardActor.h`
	- `Source/BrawlEconomy/Public/Components/BrawlShopComponent.h`
	- `Source/BrawlEconomy/Public/Components/BrawlTraitComponent.h`

## Tasks (references-only)
1) Create the `BrawlUI` module
	- New folder: `Source/BrawlUI/` (Public/Private)
	- New build rules: `Source/BrawlUI/BrawlUI.Build.cs`
	- Register module in `Brawl.uproject` Modules list

2) MVVM implementation approach
	- UE MVVM plugin (preferred if available/enabled)

3) Implement v0 ViewModels (names per `rules/brawl-directories-2.md`)
	- `BrawlVM_RoundTimer`
		- Inputs: `ABrawlGameState` (`PhaseTag`, remaining time)
	- `BrawlVM_Traits`
		- Inputs: `ABrawlPlayerState` -> `UBrawlTraitComponent` entries (`TraitTag`, `ActiveCount`, `PotentialCount`)
		- Display format goal: `Active(Potential)/NextThreshold`
	- `BrawlVM_Shop`
		- Inputs: `ABrawlPlayerState` -> `UBrawlShopComponent` offers (OfferId, UnitDataId, cost)
	- `BrawlVM_Board`
		- Inputs: `ABrawlBoardActor` occupancy mapping
		- Represent bench + field occupancy using canonical `FBrawlGridCoord` (not actor transforms)

4) Create a debug overlay widget (Content)
	- Example asset: `WBP_BrawlDebugOverlay`
	- Bind to ViewModels and show:
		- Phase + time remaining
		- Trait list
		- Shop offers
		- Board occupancy (text grid is fine)

5) Define how the overlay is spawned/toggled without coupling gameplay modules to UI
	- Preferred: a BrawlUI-owned `UGameInstanceSubsystem` or `ULocalPlayerSubsystem` that spawns the widget on the owning client
	- Acceptable early/dev: a `LVL_Sandbox`-only Blueprint hook that adds overlay on BeginPlay

## Acceptance criteria
- `BrawlUI` compiles and loads.
- In LVL_Sandbox PIE, overlay displays and updates as replicated state changes.
- No gameplay module includes headers from `BrawlUI`.

# Workstream C — Traits v2 (thresholds + effects)

## Objective
Extend traits beyond counting so thresholds can apply **server-authoritative effects** (GameplayEffects / ability grants / tags), while preserving Active vs Potential semantics.

## Rules / constraints
- Effects apply from **ActiveCounts only** (field-only).
- PotentialCounts remain UI-only.
- Effects must be applied/removed idempotently and deterministically.

## Primary references
- Current v1 trait counting:
	- `Source/BrawlEconomy/Public/Components/BrawlTraitComponent.h`
	- `Source/BrawlEconomy/Private/Components/BrawlTraitComponent.cpp`
	- `Source/BrawlEconomy/Public/Data/BrawlTraitData.h`
	- `Source/BrawlEconomy/Private/Data/BrawlTraitData.cpp`
- Data schema requirements:
	- `rules/brawl-data-model-contract.md` (“TraitData (UBrawlTraitData)”, thresholds -> effects)
- Active vs Potential contract + triggers:
	- `rules/brawl-implementation-2.md` (“Traits: active vs potential”)
	- `rules/brawl-economy-contract.md` (“Trait counting semantics”)

## Decision points (STOP and confirm in implementation)
- Threshold application model:
	- highest tier only (recommended; tiered, replaces previous)
- Effect target set:
	- Option A: only units that contribute the trait tag
	- Option B: optionally, all owned field units (for some traits/thresholds eg 3 = +5% Attack Speed for same trait, 6 = 10% same trait, 9 = 15% same trait and 5% other units)
	- Option C: a team-level ASC (if/when introduced)

## Tasks (references-only)
1) Expand `UBrawlTraitData` so each threshold can author effects
	- Effects allowed (v1): GameplayEffect list, ability grants, tag adds/removes
	- Keep it designer-authored and data-driven; avoid hardcoding trait names in code

2) Implement apply/remove in the recompute path
	- Entry point remains server-only (`UBrawlTraitComponent` via `ABrawlPlayerState::ServerRecomputeTraits()`)
	- Track which tier/effects are currently applied so recompute can:
		- apply newly-activated tier effects
		- remove deactivated tier effects
	- When iterating units, sort deterministically by `FBrawlUnitInstanceId.Value`

3) Define how effects are represented on units
	- Recommended: apply GameplayEffects to the unit’s ASC (replicated via GAS)
	- Ability grants should follow the established pattern used by `UBrawlUnitLoadoutComponent` (grant handles tracked so they can be removed cleanly)

## Acceptance criteria
- Crossing a threshold in ActiveCounts applies the authored effects.
- Dropping below a threshold removes the effects.
- PotentialCounts never drive effects.

## Test expectations
- Add LVL_Sandbox automation tests to assert:
	- effects are applied only while the unit is on the field
	- effects are removed when the unit returns to bench
	- deterministic behavior when multiple units are involved

# Workstream D — Items v1 (ItemData + equip/apply pipeline)

## Objective
Introduce a minimal item system: DataAsset definition + server-authoritative equip/unequip pipeline + effect application on units.

## Rules / constraints
- Server validates and commits all item equips.
- Items are data-driven (PrimaryAssetIds).
- Keep v1 scoped: a single unit item slot is acceptable.

## Primary references
- Item schema:
	- `rules/brawl-data-model-contract.md` (“ItemData (UBrawlItemData)”) 
- Server validation patterns:
	- `rules/brawl-server-validation-checklist.md` (request validation model)
- Existing ability grant pattern:
	- `Source/BrawlUnit/Public/Components/BrawlUnitLoadoutComponent.h`
	- `Source/BrawlUnit/Private/Components/BrawlUnitLoadoutComponent.cpp`

## Decision points (STOP and confirm in implementation)
- Slots:
	- 1 item slot per unit (recommended v1)
- Uniqueness:
	- Unique per unit not unique per team/player
- Item acquisition scope:
	- v1 equip pipeline only (no shop integration)
	- optionally include a minimal acquisition flow (spawn an item into inventory for testing)

## Tasks (references-only)
1) Create `UBrawlItemData : UPrimaryDataAsset`
	- Suggested location: `Source/BrawlEconomy/Public/Data/` (or another module if you prefer, but keep it consistent with `rules/brawl-directories.md` ownership intent)
	- Fields per contract: unique flag, GameplayEffects, ability grants, tags
	- Ensure AssetManager scanning is configured for the Item primary asset type

2) Define item ownership + equip state
	- Recommended: replicate equipped item id(s) on `ABrawlUnitCharacter` as `FPrimaryAssetId` (stable + replay friendly)
	- Implement a server RPC on `ABrawlPlayerController` to request equipping an item onto a unit

3) Apply/remove item effects on the server
	- Recommended pattern: a `BrawlUnit` component responsible for applying/removing item effects to the unit’s ASC when equipped id changes
	- Effects should be reversible (handles tracked for removal)

## Acceptance criteria
- Equipping an item updates replicated equipped item id(s) and applies authored effects.
- Unequipping removes effects.
- Invalid equip requests are rejected (wrong phase, not owned, invalid item id).

## Test expectations
- Add LVL_Sandbox automation test(s) to validate equip/unequip applies a known tag/effect and removes it.
