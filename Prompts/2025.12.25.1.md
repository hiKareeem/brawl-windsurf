## A) Workstream B2 — Arena transfer orchestration (server authoritative)

### B2 “definition of done” (expanded)
- **Determinism**: every transfer/return applies in stable order (sort by `FBrawlUnitInstanceId.Value`) and never depends on iteration order of `TActorIterator` / `TMap`.
- **Single source of truth**: **board occupancy** drives positioning; unit transforms are snapped from occupancy.
- **No ownership changes**: roster ownership stays with [ABrawlPlayerState](cci:1://file:///E:/Unreal/BrawlFinal/Brawl/Source/BrawlMatch/Private/Game/BrawlPlayerState.cpp:43:0-52:1); only occupancy/board association changes.
- **Correct interaction board**: both players’ `ActiveBoardActor` must point at the arena board during combat, and return afterwards.
- **Correct host/guest identity**: arena board’s `HostPlayerId` / `GuestPlayerId` must match the pairing so bench-row validation works.

### B2 suggested sub-workstreams (so you can prompt them cleanly)
- **B2.1 — Coordinate mapping contract & helpers**
    - **Deliverable**: a single “canonical mapping” function used by both transfer and return.
    - **Must cover**:
        - bench coords mapping (guest bench mirrored X + fixed row)
        - field coords mapping (180° rotation into opponent half)
    - **STOP/confirm**: exact field mapping math (see questions below).

- **B2.2 — Transfer plan representation**
    - **Deliverable**: a match-owned structure that captures:
        - `UnitId`
        - `FromBoard`, `FromCoord`
        - `ToBoard`, `ToCoord`
        - `OwnerPlayerId` (for validation/debug)
    - **Must**: support restoring even if the unit later dies (i.e., return logic must handle missing actors/removed units gracefully).

- **B2.3 — Combat start hook**
    - **Deliverable**: on entering `Phase.Combat`:
        - choose arena host board for a pairing
        - set arena board `HostPlayerId/GuestPlayerId`
        - move guest player’s units (bench + field) from their home board to arena host board
        - set both PlayerStates’ `ActiveBoardActor` to arena host board

- **B2.4 — Combat end hook / return**
    - **Deliverable**: on leaving combat (entering `Phase.Rewards`):
        - return transferred units to original boards/coords
        - set `ActiveBoardActor` back to home boards
    - **Decision**: whether death cleanup happens before/after return (see questions).

- **B2.5 — Automation test**
    - **Deliverable**: LVL_Sandbox latent test verifying:
        - precombat occupancy snapshot on home boards
        - post-transfer occupancy on arena board (including mirrored coords)
        - post-return occupancy restored exactly

## Decision points
### Confirmed decisions (2025-12-25)
- **A1 coord mapping (guest -> arena host board)**
    - **Field** (180° rotation):
        - `X' = FieldWidth - 1 - X`
        - `Y' = (2*FieldHalfHeight - 1) - Y`
        - Example (9x8 field): `(0,0) -> (8,7)`
    - **Bench** (mirror X + fixed guest row):
        - `X' = BenchWidth - 1 - X`
        - `Y' = 1` (guest bench row)

- **A2 host selection**
    - Deterministic host/guest designation per pairing so each player hosts about half the time.
    - Suggested implementation: `Hash(MatchId, RoundIndex) % 2`.

- **A3 clearing home board**
    - After transfer, the guest home board occupancy is cleared.

- **A4 combat end**
    - Combat can end early only when one side has no alive field units **on all arena boards**.
    - Do not advance phase while any arena fight is still ongoing.
    - Add a victory marker tag (suggested: `State.Victory`) to disable AI/targeting and play victory presentation.

- **A5 death handling**
    - Dead units are not destroyed; prefer leaving them in occupancy but tagged dead.
    - After battle, all dead units are reset/respawned on the home board to full health/etc.

- **A6 sandbox migration**
    - Remove/migrate legacy sandbox arena setup; sandbox should rely on RoundManager phase transitions and the B2 transfer/return system.

# Workstream F2 — Combat Resolution v2: Winner/Tie + Rewards Phase Semantics

## Objective
Define and implement:
- how combat outcome is decided
- what Rewards phase does with that outcome
- (optional) early-out combat when one team is eliminated

## Decision Points
- Timer-only combat vs early-out on elimination
  - Early-out on elimination of ALL BATTLES (ie all 4 arena fights in an 8-player game). We don't want to advance phase while fights are ongoing.
- Tie rules (draw? sudden death? deterministic tiebreak?)
  - Sudden death, ideally TFT-like and designer defined (eg 15 seconds of overtime with stacking attack speed, decreased health regen etc to finish the fight after the allotted 60 seconds). If needed, we can have a backup of more units wins, followed by more unit health wins, followed by UnitId or some other deterministic metric.
- Are shop actions allowed during Rewards? 
  - No. Rewards is being treated as a post-combat teardown, rewards distribution, and planning setup phase. We should not allow shop actions to occur to prevent issues with arena transfer orchestration.
