# StarCombine v1 — Automatic TFT-style Combines (Combine Plan + Reservation + Chain)

## Locked Policy Decisions (as of 2025.12.21)
- **Automatic combines:** resolves are automatic (no explicit “pick 3 units” API).
- **Anchor selection (priority):**
	1) If any candidate copy exists on the **field**, anchor is a **field** copy.
		- If multiple field copies exist: prefer **field w/ item equipped** (later), then **field w/o item**.
		- Tie-breaker: deterministic (stable) order.
	2) If no field copies exist (bench-only triple): anchor is the **newly acquired unit**.
		- Tie-breaker: deterministic (stable) order.
- **Reservation:** deferred combines must reserve the specific units (prevent “sell 2 copies mid-combine” exploits).
- **Chain combines:** after a successful combine, immediately attempt follow-on combines (including 2→3-star chains).

**Rules Applied:** `brawl-implementation.md` (Star combine policy + combat deferral), `brawl-directories.md` (module boundaries), `brawl-replication-contract.md` (server authority)

# Workstream A — StarCombine v1: Automatic Combine Detection + Deterministic Combine Plan

## Objective
Implement a server-authoritative “rules engine” that:
- Detects `3x` copies of the same unit for a player
- Selects **anchor** + **consumed** units deterministically using the locked policy
- Produces an executable **combine plan**
- Immediately executes the plan **only if allowed** (see deferral rules below)
- Otherwise, queues it as a **pending combine** (reserved) for next `Phase.Planning`

## Constraints
- **Server-only** (clients never author combines).
- **No module dependency violations**:
	- `BrawlUnit` must not depend on `BrawlMatch` or `BrawlGrid`.
	- Use `IBrawlGridOccupantInterface` + `IBrawlMatchContextInterface` (both in `BrawlCore`) for bench/field + phase.
	- For execution (consuming units / clearing occupancy / updating roster), use a **BrawlCore interface** implemented by `ABrawlGameState` (see Workstream B).
- **Defer rule:** if `PhaseTag == Phase.Combat` AND **any involved unit is on the field** (or placement unknown), do **not** execute now; create a pending combine (reserved).
- **Determinism:** when multiple combines are possible, resolution order must be stable (sort by stable IDs / asset IDs).
- **Item preference is “later”:** design the selection code to accept a `bHasItemEquipped` signal, but for v1 it can default to false.

## Files
- Add:
	- `Source/BrawlCore/Public/Types/BrawlStarCombineTypes.h`
		- `FBrawlStarCombineKey` (UnitDataId + StarLevel)
		- `FBrawlStarCombinePlan` (anchor + 2x consumed + desired star)
		- `FBrawlPendingStarCombine` (reservation + deferral payload)
- Update:
	- `Source/BrawlUnit/Public/Components/BrawlStarCombineComponent.h`
	- `Source/BrawlUnit/Private/Components/BrawlStarCombineComponent.cpp`

## Tasks
1) **Define the minimal data model (plan + pending + key)**
	- `FBrawlStarCombineKey`:
		- `FPrimaryAssetId UnitDataId`
		- `int32 StarLevel`
	- `FBrawlStarCombinePlan`:
		- `int32 OwnerPlayerId`
		- `FPrimaryAssetId UnitDataId`
		- `int32 FromStarLevel`
		- `int32 ToStarLevel` (`FromStarLevel + 1`, clamped 1..3)
		- `FBrawlUnitInstanceId AnchorUnitId`
		- `FBrawlUnitInstanceId ConsumedUnitIdA`
		- `FBrawlUnitInstanceId ConsumedUnitIdB`
		- `FBrawlUnitInstanceId NewlyAcquiredUnitId` (optional/invalid when unknown)
	- `FBrawlPendingStarCombine`:
		- `FBrawlStarCombinePlan Plan`
		- `TSet<FBrawlUnitInstanceId> ReservedUnitIds` (or equivalent in component state)

2) **Expose a simple server-facing entrypoint**
	- Add a server-only API to the component (name is flexible; choose one and stick to it):
		- `void NotifyUnitAcquired(FBrawlUnitInstanceId NewlyAcquiredUnitId);`
			- Expected call sites later: shop purchase, reward grants, debug spawn helpers.
			- This function triggers combine detection + resolution loop for that player.
	
3) **Gather owned-unit candidates without depending on Match/Grid**
	- Within `BrawlUnit`, gather candidates by scanning unit actors in the world:
		- Iterate `TActorIterator<ABrawlUnitCharacter>`
		- Keep only units with:
			- `OwnerPlayerId == TargetPlayerId`
			- valid `UnitDataId`
			- valid `UnitId`
	- Derive placement (bench vs field) via `IBrawlGridOccupantInterface` snapshot:
		- Snapshot missing => treat as **field** (conservative for combat deferral).
	- Define a small internal “view” struct used for sorting:
		- `UnitId`
		- `UnitDataId`
		- `StarLevel`
		- `bIsOnBench` (false if unknown)
		- `bHasItemEquipped` (v1: false; later: real query)
		- `bIsNewlyAcquired`

4) **Group candidates by (UnitDataId + StarLevel)**
	- Build `TMap<FBrawlStarCombineKey, TArray<UnitView>>`.
	- Exclude any units already reserved by pending combines.

5) **Select anchor deterministically using the locked policy**
	- Define `AnchorRank(UnitView)` as a stable sortable tuple (lower is better):
		1) `bIsOnField && bHasItemEquipped`
		2) `bIsOnField && !bHasItemEquipped`
		3) `bIsOnBench && bIsNewlyAcquired`
		4) `bIsOnBench && !bIsNewlyAcquired`
		5) tie-break: `UnitId.Value` ascending
	- Pick the unit with the best (lowest) rank.
	
6) **Select consumed units deterministically**
	- After choosing anchor, choose 2 consumed units from the remaining copies.
	- Recommended v1 policy (unless you deliberately choose a different one):
		- Prefer consuming bench copies first.
		- Prefer consuming copies without items first.
		- Tie-break: `UnitId.Value` ascending.
	- Ensure consumed units are distinct, valid, and not the anchor.

7) **Decide “execute now vs defer” using phase + placement of all 3 units**
	- Use `IBrawlMatchContextInterface` (`World->GetGameState()` implements it).
	- Defer if:
		- `PhaseTag == Phase.Combat` AND
		- any of `{Anchor, ConsumedA, ConsumedB}` is on **field** (or placement unknown)

8) **Chain combine loop**
	- If a plan is executed immediately:
		- Recompute groups for the same player and keep resolving until no eligible group remains.
		- Hard cap the loop per call (safety) to prevent infinite loops if bugs occur (e.g., max 100 combines).
	- The chain loop must remain deterministic:
		- Sort keys by `UnitDataId` then `StarLevel` then anchor `UnitId`.

## Acceptance Criteria
- Calling `NotifyUnitAcquired(NewUnitId)` can produce and resolve 1+ combines for that player.
- Anchor selection follows the locked policy:
	- Any field copy exists => anchor is field.
	- Bench-only triple => anchor is the newly acquired unit.
- Deferral is triggered by combat + any field involvement.
- Resolution is deterministic given the same world state.

**Rules Applied:** `brawl-implementation.md` (Star combine policy), `brawl-directories.md` (no module coupling), `brawl-replication-contract.md` (server authority)

# Workstream B — Combine Execution: Consume Units + Update Board/Roster + Upgrade Anchor

## Objective
Provide a server-authoritative execution path for `FBrawlStarCombinePlan` that:
- Clears board occupancy for consumed units
- Unregisters + destroys consumed unit actors
- Updates player roster to remove consumed units
- Applies the anchor star upgrade (and keeps audit event emission intact)

## Constraints
- `BrawlUnit` must not call into `BrawlMatch`/`BrawlGrid` types.
- Execution must be callable from `UBrawlStarCombineComponent` via a **BrawlCore interface** implemented in `BrawlMatch`.
- Execution must be fully **server-only** and must leave replicated state consistent.

## Files
- Add:
	- `Source/BrawlCore/Public/Interfaces/BrawlStarCombineExecutorInterface.h`
- Update:
	- `Source/BrawlMatch/Public/Game/BrawlGameState.h`
	- `Source/BrawlMatch/Private/Game/BrawlGameState.cpp`
	- `Source/BrawlGrid/Public/Actors/BrawlBoardActor.h`
	- `Source/BrawlGrid/Private/Actors/BrawlBoardActor.cpp`
	- (optional) `Source/BrawlMatch/Public/Game/BrawlPlayerState.h/.cpp` (if you add helper methods)

## Tasks
1) **Define an executor interface in BrawlCore**
	- `IBrawlStarCombineExecutorInterface` should expose at minimum:
		- `virtual bool ExecuteStarCombinePlan(const FBrawlStarCombinePlan& Plan) = 0;`
	- Implementation must validate the plan (owner, unit IDs, unit data IDs, etc.) before mutating state.

2) **Implement the interface on `ABrawlGameState` (BrawlMatch)**
	- `ABrawlGameState` already exists as the cross-module “match context” object and already owns the StarCombine component.
	- `ExecuteStarCombinePlan` responsibilities:
		- Locate `ABrawlUnitCharacter` for `AnchorUnitId`, `ConsumedA`, `ConsumedB`.
		- Validate:
			- All 3 exist, have authority, match `OwnerPlayerId` and `UnitDataId` and `FromStarLevel`.
			- All 3 are distinct.
		- For each consumed unit:
			- Clear board occupancy (see task 3).
			- Unregister unit actor from board (clears grid snapshot).
			- Destroy actor (alternatively, pool it in a unit actor pool, NOT the shop pool).
			- Remove from `ABrawlPlayerState` roster.
		- Upgrade anchor:
			- Prefer calling `UBrawlStarCombineComponent::RequestStarLevelUpgrade(AnchorId, ToStarLevel)` so the existing audit event emission path is reused.
			- Update roster entry for anchor (set `StarLevel`), if roster does not automatically follow the unit.

3) **Add an explicit server-only board API to remove a unit from occupancy**
	- `ABrawlBoardActor` currently has internal occupancy mutation but not a clean gameplay removal API.
	- Add something like:
		- `bool ServerRemoveUnit(FBrawlUnitInstanceId UnitId);`
			- clears the occupancy slot (if present)
			- (optionally) unregisters the actor mapping
	- This keeps occupancy, mapping, and snapshot consistent.

## Acceptance Criteria
- After executing a plan:
	- Consumed units are removed from occupancy and destroyed/pooled.
	- Consumed units are removed from roster.
	- Anchor’s StarLevel is increased and remains in roster.
	- No stale occupancy references remain.

**Rules Applied:** `brawl-directories.md` (ownership boundaries), `brawl-replication-contract.md` (occupancy/roster consistency), `brawl-implementation.md` (server authority)

# Workstream C — Reservation + Pending Combines (Combat Deferral)

## Objective
Extend `UBrawlStarCombineComponent` so deferred combines:
- Reserve the *specific* 3 unit IDs involved
- Persist across `Phase.Combat`
- Resolve at the start of next `Phase.Planning`

## Constraints
- Reservation is **server-only**.
- Reservation must be queryable by other server systems (e.g., sell requests).
- Pending combines resolve deterministically.

## Files
- Update:
	- `Source/BrawlUnit/Public/Components/BrawlStarCombineComponent.h`
	- `Source/BrawlUnit/Private/Components/BrawlStarCombineComponent.cpp`
	- `Source/BrawlMatch/Private/Components/BrawlRoundManagerComponent.cpp` (ensure `ResolvePendingCombines()` is called when entering `Phase.Planning`)

## Tasks
1) **Reservation state**
	- Add:
		- `bool IsUnitReservedForCombine(FBrawlUnitInstanceId UnitId) const;`
		- Internal storage:
			- `TMap<FBrawlUnitInstanceId, int32 ReservationRefCount>` (or `TSet` if you ensure uniqueness)

2) **Pending combine queue**
	- Store `FBrawlPendingStarCombine` entries.
	- When deferring a plan:
		- Add the pending entry
		- Reserve all 3 unit IDs

3) **Resolve pending combines at planning start**
	- Add `ResolvePendingCombines()` and call it from the existing planning-phase hook.
	- Deterministic order suggestion:
		- Sort by `Plan.AnchorUnitId.Value` ascending
		- then by `Plan.UnitDataId` / `Plan.FromStarLevel`
	- For each pending entry:
		- Validate units still exist and still match the plan invariants.
		- If valid: execute via the executor interface (Workstream B).
		- Always unreserve on success or cancellation.

4) **Sell-prevention integration (required v1)**
	- Implement a minimal server RPC:
		- `ABrawlPlayerController::ServerRequestSellUnit(FBrawlUnitInstanceId UnitId)`
	- Validations (server-derived; do not trust client):
		- PlayerState exists
		- Unit exists and is owned by the requesting player
		- Phase allows selling (Disabled only during Rewards for bench units and additionally Combat for field units actively fighting)
		- Reject if the unit is reserved for a pending combine:
			- `if (GameState->GetStarCombineComponent()->IsUnitReservedForCombine(UnitId)) return;`
	- Commit:
		- Remove unit from board occupancy
		- Unregister + destroy the unit actor
		- Remove from roster
		- Refund gold (v1 can be UnitData Cost)
		- Return the unit to the shared pool (shop pool)
		- Emit `Economy.Sell` with `Refund`

## Acceptance Criteria
- A combat-field-involved combine is queued and reserved (no immediate consumption/upgrade).
- Reservations persist until planning.
- On planning start, pending combines resolve and reservations clear.

**Rules Applied:** `brawl-implementation.md` (defer combines to planning), `brawl-replication-contract.md` (server authority), `brawl-server-validation-checklist.md` (deny invalid requests)
