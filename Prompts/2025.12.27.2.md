## Workflow 1 — Combat: implement `State.Victory` (stop AI/targeting for “already won” arenas)

**Prompt to give an AI assistant**

You are implementing the missing **Victory-state semantics** described in the Brawl rules.

### Goal
When an arena fight ends early (one side eliminated) but other arenas may still be fighting:
- Apply `State.Victory` to the **surviving winning-side field units** on that arena.
- Units with `State.Victory` should:
  - stop combat decision-making (no more casts / target selection)
  - stop being considered “active combatants” for any remaining combat resolution logic
  - be eligible for victory presentation (animation/cosmetics can be deferred)

### Rules / references
- `rules/brawl-implementation-2.md` (Combat phase: “apply `State.Victory` to surviving units after their arena fight ends”)
- `rules/brawl-gameplay-tags-contract.md` (required tag: `State.Victory`)
- `rules/brawl-replication-contract.md` (server authority + replay expectations)

### Starting points in code
- Tag definitions:
  - `Source/BrawlCore/Public/BrawlGameplayTags.h`
  - `Source/BrawlCore/Private/BrawlGameplayTags.cpp`
- Arena resolution:
  - `Source/BrawlMatch/Private/Components/BrawlCombatManagerComponent.cpp` (arena resolve + `Combat.ArenaResolved`)
- Unit combat decision loop:
  - `Source/BrawlUnit/Private/Components/BrawlUnitCombatBrainComponent.cpp` (combat brain tick gating)
- Targeting:
  - `Source/BrawlAbilities/Public/Data/BrawlTargetingPolicy.h` + `Private/Data/BrawlTargetingPolicy.cpp`

### Requirements
- Add and register gameplay tag `State.Victory` in BrawlCore.
- On arena resolve:
  - determine the winning `PlayerId` (already computed in `FBrawlArenaCombatResolution`)
  - apply the tag to surviving **winning** units that are:
    - alive
    - on the **field** (bench excluded)
    - on that arena board
- Ensure the tag is cleared at an appropriate time:
  - at combat teardown / return to planning (recommended)
  - do not allow the tag to “stick” into the next round
- AI/targeting behavior:
  - units with `State.Victory` must not attempt to acquire targets or cast abilities
  - conservative approach: short-circuit combat brain logic when tag is present

### Deliverables
- `State.Victory` tag added (BrawlCore).
- Victory tag application + clearing integrated into match combat flow.
- Automation test(s) verifying:
  - tag is applied to winning-side survivors when an arena resolves
  - tagged units stop producing combat actions (no further cast/damage events from them after resolution)

### Acceptance criteria
- In LVL_Sandbox automation, when an arena resolves early:
  - `State.Victory` appears on the expected units’ ASC tags
  - those units do not continue casting while other arenas could still be running
  - tag is removed before next `Phase.Planning`

### Out of scope
- Victory animations / cosmetic cues (presentation only).
- Adding new event log schema types.

## Workflow 2 — Match artifacts: stage replay + event log for GameLift-collected server logs

**Prompt to give an AI assistant**

You are implementing **artifact staging** so match outputs can be collected/uploaded by GameLift (or any “collect this folder” server-log system) without changing replay/event log generation.

### Goal
On match end (server-only), stage artifacts into a single directory under `Saved/`:
- JSONL match event log file(s)
- Replay recording artifacts (DemoNetDriver replay)

### Rules / references
- `rules/brawl-event-log-schema.md` (export path + JSONL rules)
- `rules/brawl-implementation.md` (replay + event log artifacts on match end)

### Starting points in code
- Match end hook:
  - `Source/BrawlMatch/Private/Game/BrawlGameMode.cpp` (`HandleMatchEnded`, `TryExportMatchEventLog`, replay stop)
- Replay recording wrapper:
  - `Source/BrawlNet/Public/Subsystems/BrawlReplaySubsystem.h`
  - `Source/BrawlNet/Private/Subsystems/BrawlReplaySubsystem.cpp`
- Net settings:
  - `Source/BrawlNet/Public/BrawlNetSettings.h`
- Existing automation coverage:
  - `Source/BrawlMatch/Private/Tests/BrawlMatchArtifactsAutomationTest.cpp`

### Requirements
- Add a config setting (in `UBrawlNetSettings`) for an artifact staging subdir (example default: `BrawlServerLogs`).
- Implement a staging step on match end that:
  - creates `Saved/<StagingSubdir>/...`
  - copies (not moves) exported event logs and replay outputs into staging
  - is tolerant to missing artifacts (log warning, do not crash)
- Keep staging server-only.

### Deliverables
- `UBrawlNetSettings` extended with a staging subdir.
- `ABrawlGameMode` (or helper) stages artifacts after:
  - replay stop
  - event log export
- Extend/adjust `BrawlMatchArtifactsAutomationTest` to assert staging ran (use debug flags or observable side-effects appropriate for automation).

### Acceptance criteria
- In automation:
  - match end triggers replay stop + event log export (existing test)
  - staging step is invoked and reports success/failure deterministically via logs/flags

### Out of scope
- Actual GameLift SDK upload.
- Cloud persistence/backoff/retry policies.

## Workflow 3 — v2 hardening: perf + server-validation sweep (small, targeted)

**Prompt to give an AI assistant**

You are performing a targeted **v2 hardening pass** focusing on performance and server-request validation.

### Goal
- Ensure core combat/placement systems remain viable at the v2 target scale (and don’t block v3 scaling work).
- Close obvious validation gaps for client RPC requests (anti-abuse posture).

### Rules / references
- `rules/brawl-performance-budgets.md` (avoid per-unit tick where possible; avoid per-frame sorting)
- `rules/brawl-server-validation-checklist.md` (server-only commit + validation)
- `rules/brawl-replication-contract.md` (do not rely on distance-only replication assumptions)

### Starting points in code
- Combat driver tick gating:
  - `Source/BrawlMatch/Private/Components/BrawlCombatManagerComponent.cpp`
- Per-unit combat decisions:
  - `Source/BrawlUnit/Private/Components/BrawlUnitCombatBrainComponent.cpp`
- Server request validation gates:
  - `Source/BrawlMatch/Private/Game/BrawlPlayerController.cpp` (placement/shop/equip requests)

### Requirements
- Performance sweep:
  - identify any per-tick sorting/iteration that can be made cheaper (cache sorted lists when safe)
  - ensure per-unit tick is strictly gated to `Phase.Combat` and does not run in `Phase.Planning`
  - ensure debug overlays / debug ticks are behind cvars and default-off
- Validation sweep:
  - confirm every server RPC validates:
    - phase legality
    - ownership (player owns unit / board row)
    - bounds / capacity rules (bench row, field lock)
  - add minimal rate limiting hooks if missing (even if just TODO-backed counters/cvars)

### Deliverables
- A small set of focused changes (not a refactor) that reduce obvious hot paths.
- Improved logs for rejected requests (stable IDs, player id, phase tag).
- One or more automation tests that act as “gates” for the hardening changes (only where practical).

### Acceptance criteria
- No per-unit combat brain tick in non-combat phases (unless explicitly forced by a debug cvar).
- Server RPCs reject invalid requests deterministically with clear logs.
- No new gameplay rules are introduced; only hardening / compliance with existing contracts.

### Out of scope
- ReplicationGraph implementation (v3 work).
- Large architectural rewrites.
