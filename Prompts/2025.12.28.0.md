# 2025.12.28.0 — Next Workflows (v4-facing prompts)

---

These are **three workflows** to start v4 work after the remaining v3 follow-ups (replication policy + multi-arena test stabilization + spectator UX).

Assumptions / decisions already made:
- Dedicated server authority: clients send requests only; server validates and commits.
- Deterministic ordering where resolution order matters (sort by stable `FBrawlUnitInstanceId`).
- Season gating is a real feature: start with a “Season 0” allowlist.
- Odd-player rule intent (draft): TFT-like “ghost roster” (details need confirmation).

## Workstream 1 — Economy: Season 0 gating (SharedPool + Shop never roll units outside allowlist)

### Objective
Implement a Season DataAsset that allowlists which Unit PrimaryAssets exist in the match’s shared pool, so that:
- SharedPool composition is derived from the active season allowlist.
- Shop rolls never produce units outside the allowlist.

### Constraints / invariants
- Server-only authority: clients never provide RNG outcomes.
- Deterministic / auditable RNG: any randomness remains server-seeded and loggable.
- No new GameplayTags, Attributes, or new modules.

### Primary references
- `rules/brawl-plan.md` (v4.0 Season 0 gating)
- `rules/brawl-data-model-contract.md` (PrimaryAsset identity + “how to add content”)
- `Source/BrawlEconomy/Public/Subsystems/BrawlSharedPoolSubsystem.h`
- `Source/BrawlEconomy/Public/Components/BrawlShopComponent.h`
- `Config/DefaultGame.ini` (AssetManager scanning rules)

### Deliverables
- A new Season DataAsset type (PrimaryDataAsset) that contains:
  - an allowlist of Unit `FPrimaryAssetId`s
  - any season metadata needed for logging/debug (name/version)
- A match-level selection mechanism for ActiveSeason (server authored).
- SharedPool composition builder updated to use ActiveSeason allowlist.
- Shop offer rolling updated to draw only from the season-scoped pool.
- Automation coverage (LVL_Sandbox or unit-style) proving:
  - with ActiveSeason allowlist = {A, B, C}, offers never include units outside {A, B, C}

### Acceptance criteria
- With a fixed seed and an allowlist, shop rolls are deterministic and never output disallowed units.
- Pool counts only exist for allowlisted units.

### Rules Applied
- `rules/brawl-implementation.md` (server authority; RNG policy)
- `rules/brawl-data-model-contract.md` (content authoring pipeline)

## Workstream 2 — Content pipeline: “Content validity gate” (fail-fast when assets are invalid)

### Objective
Add a lightweight validation gate that loads all relevant PrimaryAssets and asserts required fields exist, so content can be added without silently breaking gameplay.

### Constraints / invariants
- Validation must be deterministic and runnable in automation.
- Do not introduce new gameplay systems.
- The validation should live in C++ (systems side), but validate DataAssets authored in editor.

### Primary references
- `rules/brawl-data-model-contract.md` (required schema fields)
- `rules/brawl-testing-matrix.md` (automation expectations)
- Asset types:
  - Unit, Ability, Item, Trait, Season

### Deliverables
- A validation function/test that:
  - enumerates all PrimaryAssets (by type)
  - loads them (synchronously in automation)
  - validates required fields and invariants (examples):
    - UnitData: cost, tags, curve refs (as required by contract)
    - AbilityData: kind tags, cooldown/power, targeting policy refs
    - ItemData/TraitData: required identifiers/tags
    - SeasonData: allowlist non-empty (for Season 0)
- Clear error messages that point to the specific asset id/path and missing field.

### Acceptance criteria
- Adding an invalid asset causes the validation gate to fail deterministically with an actionable error.

### Rules Applied
- `rules/brawl-data-model-contract.md`
- `rules/brawl-testing-matrix.md`

## Workstream 3 — Match: odd-player “ghost roster” pairing (TFT-like)

### Objective
Define and implement the odd-player rule such that when there is an odd number of active players:
- One player fights a “ghost roster” snapshot of another actively fighting player.

Confirmed intent:
- The ghost fight outcome affects **only the unpaired player** (life/streak/etc.).
- The “source” player whose roster was copied is **not affected** (purely a snapshot/opponent).

### Primary references
- `rules/brawl-plan.md` (target: v4.3 per current user intent)
- `rules/brawl-implementation.md` (server authority; replay expectations)
- `rules/brawl-event-log-schema.md` (ArenaResolved + deterministic ordering)

### Clarification
- Ghost fights count toward win/loss streaks for the non-ghost player.
- Ghost source selected by
  - deterministic seeded choice among currently-fighting players
  - exclude the unpaired player’s last opponent
- The ghost roster snapshot includes
  - only field units

### Replication / visibility note (ties into RepGraph work)
- The scoreboard should remain **player-centric**:
  - roster/bench list is visible even if the unit actors are currently away on a different arena board.
- Unit actors are visible based on ReplicationGraph/scouting:
  - at minimum: actors on the viewer’s currently selected/scouted board are relevant.
  - optionally (perf permitting): actors for multiple/all concurrent battles can remain relevant so the player can look around and see multiple fights.

### Deliverables (once decisions are confirmed)
- Pairing logic updated to generate a ghost pairing when odd.
- Transfer plan updated to spawn a ghost snapshot without mutating the source player’s actual combat.
- Event logging for the ghost arena resolution that is replay/audit friendly.
- Automation coverage for odd player counts.

### Acceptance criteria
- Odd player rounds resolve deterministically and do not break multi-arena phase gating.
- Ghost pairing does not mutate the source player’s live arena combat.
