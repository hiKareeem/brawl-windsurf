# 27.1 — Next Steps Prompts (v3 focus)

These are **three parallelizable workflows** for the next milestone.

Assumptions / decisions already made:
- Focus is **v3 (8-player scaling)**.
- Pairings are **deterministic pseudo-random** (seeded) for now, but should be easy to swap to Swiss/round-robin later.
- Elimination is **TFT-like**: players have Life; elimination at `Life <= 0`; match ends when **1** player remains.

Global constraints (apply to all workflows)
- Dedicated server authority: clients send requests only; server validates and commits.
- Preserve replay correctness: anything spectators/clients need must replicate (RepGraph will manage relevance).
- Deterministic ordering where resolution order matters (sort by stable `FBrawlUnitInstanceId`).
- No new modules; follow module boundaries in `brawl-directories.md`.

## Workflow 1 — BrawlNet: Implement `UBrawlReplicationGraph` (per-board relevancy + spectator routing)

**Prompt to give an AI assistant**

You are implementing the **v3 ReplicationGraph** for Brawl.

### Goal
Implement `UBrawlReplicationGraph` so that:
- A player primarily replicates:
  - their `PlayerController` + `PlayerState`
  - match-global state (`ABrawlGameState`)
  - actors on their **ActiveBoard** (and optionally their home board)
- A spectator can opt into:
  - all boards and all players’ relevant replicated state

### Rules / references
- `rules/brawl-replication-contract.md` (ReplicationGraph required; per-connection relevance)
- `rules/brawl-implementation.md` (server authoritative; replay expectations)
- `rules/brawl-directories.md` / `rules/brawl-directories-2.md` (do not invent modules/classes outside the map)

### Starting points in code
- `Source/BrawlNet/Public/Net/BrawlReplicationGraph.h` (currently empty stub)
- `Source/BrawlNet/Private/Net/BrawlReplicationGraph.cpp` (currently empty)

### Requirements
- **Do not** rely on distance-only replication for gameplay-scale (8p).
- RepGraph must handle these actor categories at minimum:
  - **Match-global:** `ABrawlGameState` (+ any match manager actors that should always be relevant)
  - **Per-board:** `ABrawlBoardActor` + its replicated occupancy, `ABrawlUnitCharacter`, projectiles (`ABrawlProjectileActor`), and other board-scoped combat actors
  - **Per-player owner-only:** `ABrawlPlayerState` and owner-only components (today)
- Relevance should be driven by **board membership**, not actor transforms.

### Design guidance
- Use `ABrawlPlayerState::GetActiveBoardActor()` as the authoritative “where this player is currently playing” pointer.
- Expect that a player can have:
  - a stable `BoardActor` (home)
  - a dynamic `ActiveBoardActor` (home or arena host board)
- Add an explicit way to mark a connection as **spectator** (or “see all boards”) that the RepGraph can query.

### Deliverables
- Implement core overrides in `UBrawlReplicationGraph` (initialize global settings, per-connection nodes, and routing for actors).
- Add a minimal routing strategy that supports:
  - “player sees only their ActiveBoard”
  - “spectator sees all boards”
- Add logging (use `LogBrawlNet`) so it’s debuggable.

### Acceptance criteria
- RepGraph is enabled and `UBrawlReplicationGraph` is actually instantiated on server.
- In a 2-player arena, each player still sees their board correctly.
- In an 8-player planning setup, bandwidth is not “replicate everything to everyone” by default.
- Spectator mode can be toggled (or stubbed) to broaden relevance to all boards.

### Out of scope (for this workflow)
- Perfect “scouting” UX.
- Advanced spatialization; start with board-scoped routing.

## Workflow 2 — BrawlMatch/BrawlGrid: v3 multi-arena orchestration (pairings + transfers + elimination)

**Prompt to give an AI assistant**

You are implementing **v3 multi-arena match flow**: 8-player planning, up to 4 concurrent arena boards in combat, deterministic pairings, and TFT-like elimination.

### Goal
- Support **8 players** in Planning (each has a home board).
- During Combat, create **N pairings** (up to 4 arenas at once) and transfer teams onto their arena host board.
- Apply rewards + life damage deterministically, eliminate players at `Life <= 0`, and end match when 1 remains.

### Pairing rule (current decision)
- Pairings are **deterministic pseudo-random**, seeded by `(MatchId, RoundIndex)`.
- Must be implemented in a way that can be swapped later to Swiss/round-robin.

### Rules / references
- `rules/brawl-implementation.md` (arena transfer mapping, combat end conditions, rewards semantics)
- `rules/brawl-event-log-schema.md` (arena resolved event + deterministic ordering)
- `rules/brawl-replication-contract.md` (ActiveBoardActor model; purchases during combat spawn on active arena bench)

### Starting points in code
- `UBrawlRoundManagerComponent` (phase/round driver)
- `UBrawlCombatManagerComponent` (arena resolve + `Combat.ArenaResolved`)
- Existing arena transfer plan + automation coverage: `BrawlArenaTransfer_RoundTripAutomationTest.cpp`
- Player life exists: `ABrawlPlayerState::Life` + `ServerApplyLifeDelta(...)`

### Requirements
- **Multiple arenas simultaneously**:
  - Do not advance phase until **all arenas** have resolved.
  - Deterministic transfer order: sort by `FBrawlUnitInstanceId.Value`.
  - Clear guest home board occupancy post-transfer to avoid duplicate authoritative occupancy.
- **Active board switching**:
  - For each player, set `ActiveBoardActor` to their arena board during combat.
  - Restore `ActiveBoardActor` to home board after combat.
- **Shop/equip interactions**:
  - Purchases during combat must spawn onto the purchaser’s allowed bench row on their **active arena board**.
- **Elimination**:
  - Apply life damage after `Combat.ArenaResolved`.
  - Mark eliminated players (Life <= 0) and exclude them from future pairings.
  - Match ends when only 1 player remains.

### Deliverables
- A deterministic pairing function (seeded shuffle) and a data structure representing the round’s pairings.
- Multi-arena transfer/return orchestration integrated into the phase flow.
- Life/elimination integrated into rewards application.
- Automation tests (LVL_Sandbox latent) covering at least:
  - 4-player setup → 2 concurrent arenas
  - no phase advance until both arenas resolved
  - life deltas applied and elimination triggers when Life hits 0

### Acceptance criteria
- With 4 players:
  - Pairings are deterministic given a fixed `(MatchId, RoundIndex)`.
  - Two arenas resolve independently, but phase advances only when both resolved.
  - Transfers return correctly (bench shuffles in combat persist).
- With 8 players (manual sandbox smoke):
  - Up to 4 arenas can run concurrently without “cross-contamination”.

### Out of scope (for this workflow)
- Swiss/round-robin fairness rules (just keep pairing logic swappable).
- RepGraph relevance policies (that’s Workflow 1).

## Workflow 3 — BrawlUI: spectator/scouting UX built on ActiveBoard + RepGraph

**Prompt to give an AI assistant**

You are implementing **spectator/scouting UX** in `BrawlUI`.

### Goal
Provide a usable in-game spectator/scouting experience:
- Switch between boards/arenas
- See scoreboard info (Life, streaks, traits, economy basics)
- Inspect a board’s occupancy/units using existing MVVM patterns

### Rules / references
- `rules/brawl-directories.md` / `rules/brawl-directories-2.md` (BrawlUI is read-only)
- `rules/brawl-replication-contract.md` (spectator visibility intent; RepGraph will handle relevance)

### Starting points in code
- `UBrawlUIDebugOverlaySubsystem` (overlay spawning/toggling)
- Existing VMs: `UBrawlVM_Board`, `UBrawlVM_PlayerEconomy`, `UBrawlVM_Traits`, `UBrawlVM_RoundTimer`

### Requirements
- **No gameplay rules in UI** (UI must be read-only).
- Board switching must be driven by authoritative replicated state:
  - if a player is scouting, they should be selecting which `ABrawlBoardActor` to view
  - do not infer from transforms
- Coordinate with Workflow 1 if replication conditions block spectators from seeing some data (many things are currently `COND_OwnerOnly`).

### Deliverables
- A spectator/scouting overlay widget flow (can be debug-first) with:
  - Board selector
  - Scoreboard list (PlayerId, Life, Level/XP/Gold if visible)
  - Selected-board panel (reuse `UBrawlVM_Board` where possible)
- New/extended ViewModels as needed (in `Source/BrawlUI/Public/UI/` + `Private/UI/`).

### Acceptance criteria
- As a spectator (or in a “spectator-like” debug mode), you can:
  - select a board
  - see its bench/field unit list update as occupancy changes
  - see the match phase + timer
- No gameplay module takes a dependency on `BrawlUI`.

### Out of scope
- Final art/UX polish (CommonUI integration can wait).
- Full replication condition refactors (only propose changes if blocking).
