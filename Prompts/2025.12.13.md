## Response 1

### Recommended architecture choices based on what you told me

### Determinism vs server-authoritative (and what “state snapshots” are)
- **“Record state snapshots”** usually means you periodically serialize enough replicated game state (plus deltas between them) so playback can reconstruct what happened without re-simulating it deterministically. In Unreal, the built-in **Replay/DemoNetDriver** effectively does this by recording network replication data and creating **checkpoints** so you can seek. It replays *what the server replicated*, not a re-simulated deterministic run.
- Given your goals (competitive integrity, spectate, full-match replays of purchases/placement/combat), the cleanest v1 is:
    1) **Server-authoritative simulation** (all real decisions happen on server).
    2) **Unreal Replay recording on the server** (gives full match playback including UI-relevant replicated events).
    3) Optional: a **parallel “event log”** (high-level structured combat+economy events) for testing and debugging.

You *can* pursue true deterministic re-simulation later, but with GAS + projectiles + navmesh movement it becomes a constraint magnet (tick order, float drift, pathing nondeterminism, ability task timing). For competitive integrity, you don’t need full determinism if the **server is the sole authority** and replays are server-recorded.

### GAS scope: combat in GAS, economy/round flow outside GAS
Use GAS where it shines:
- **Unit stats, damage formulas, buffs/debuffs, CC, auras, immunities, ability granting, tag-driven rules** → GAS.
  Keep “metagame state” as plain replicated sim state:
- **Shop offers, shared pool counts, gold/interest/streaks, XP/level, phase timers, creep wave definitions, matchmaking** → non-GAS C++ (but can still *broadcast* tags/events to GAS when they affect combat).

This keeps your “Unit + Grid reusable core” clean, and avoids turning your economy into a pile of GameplayEffects.

## The BrawlAbilities module question (pros/cons)

### Putting GAS stuff inside BrawlUnit (monolithic)
**Pros**
- Fewer modules, fewer dependency headaches
- Easy includes, faster early iteration

**Cons**
- Unit module becomes “everything combat”, harder to reuse cleanly
- Harder to share ability utilities across multiple unit types (creeps, summons, future roguelite actors)
- Compile times grow; touching ability code rebuilds the whole unit module
- UI/game flow teams end up including unit headers “just to get ability helpers”

### Separate BrawlAbilities module (recommended)
**Pros**
- Keeps **BrawlUnit** focused on “what a unit *is*” and **BrawlAbilities** on “what units *do*”
- Reuse improves: roguelite mode can reuse the exact same ability framework with different match flow
- Easier to enforce clean boundaries: abilities depend on **interfaces/tags**, not concrete UI/game mode types
- Better long-term maintainability and build times

**Cons**
- You must be disciplined about dependencies to avoid circular references

## Rules file updates

### Dedicated server authority
- All gameplay-affecting actions are validated and executed on the dedicated server.
- Clients send **intents** only (buy, move, equip ability, etc.).
- Server emits **authoritative events** into the match event stream.
- Client UI is driven from replicated state + event notifications; no client-side prediction required for planning interactions (server-confirmed is fine).

### Replay model
- Replay = **authoritative event log**, not full state snapshots.
- The replay player re-feeds the logged events to a replay-driven Match instance.
- Because navmesh and floating point can vary across platforms, we explicitly allow recording **combat decisions**:
  - target chosen for each ability cast / attack acquire
  - projectile spawn parameters
  - projectile resolved hit time and hit result (who got hit, where AoE landed)
  - any retarget/fizzle decisions
- This makes replays accurate even if the “simulation” is not strictly deterministic on a different machine.

### Combat clock
- Server maintains a canonical combat time base.
- All gameplay-relevant timings are scheduled from this clock:
  - ability cooldown completion
  - projectile travel time to impact
  - aura ticks (if any)
  - delays for channels/transform/etc.

### Speed stat
- `Spd` affects:
  1) movement speed (path following speed)
  2) cooldown modifier (global scalar applied to basic/ultimate cooldowns; exact formula data-driven but centralized)
- `Spd` does **not** change simulation tick rate; it changes ability scheduling.

### Damage formula ownership
- Use centralized global damage system implemented as:
  - GAS `ExecutionCalculation`(s) for damage
  - Optionally additional ExecCalcs per damage family if needed (phys/spec + type interactions)
- Abilities provide inputs (base power, damage class, damage type, coefficients); the ExecCalc is the single source of truth.

### Trait evaluation timing
- Trait counts recompute on:
  - unit added/removed to field
  - unit transformed into/out of a trait tag
  - unit ownership change (rare)
- UI needs two views per player:
  - **Active traits** (field only)
  - **Potential traits** (field + bench) displayed as `Active(Potential)/Breakpoint`, e.g. `2(3)/3`.
- Trait recompute produces a compact “TraitState” struct that is replicated and also written to replay for audit/debug.

- Power = ability base power (>= 0)
- ElemMult = element effectiveness multiplier (defaults to 1.0 unless a rule table says otherwise)
- Mod = product of all multiplicative modifiers from tags/effects (defaults to 1.0)
- Flat = sum of flat add/sub modifiers (defaults to 0)

Compute:
1) Ratio = clamp(A / max(D, 1), MinRatio, MaxRatio)
2) Raw = (Power * Ratio * ElemMult * Mod) + Flat
3) FinalDamage = clamp(Raw, MinDamage, MaxDamage)

All clamps are tuning constants (DataAsset):
- MinRatio (default 0.25), MaxRatio (default 4.0)
- MinDamage (default 1), MaxDamage (default large)

Note:
- If you later add armor-pen/resists, do it inside ExecCalc_Damage using tags and SetByCaller values.

---

## 4) Element effectiveness
- Element rules are data-driven (table keyed by source `Element.*` vs target `Element.*` -> multiplier).
- Default multiplier is 1.0 when no rule exists.

---

## 5) Speed policy (global)
Spd affects movement and cooldowns with a single shared reference constant `SpdRef` (default 100).

### Move speed
- MoveSpeedMultiplier = clamp(Spd / SpdRef, MinMoveMult, MaxMoveMult)
- CharacterMovement MaxWalkSpeed = BaseMoveSpeed * MoveSpeedMultiplier

### Cooldown scaling
Canonical v1 semantics: higher Spd = faster cooldowns.
- CooldownMultiplier = clamp(SpdRef / max(Spd, 1), MinCDMult, MaxCDMult)
- EffectiveCooldownSeconds = BaseCooldownSeconds * CooldownMultiplier

Tuning clamps (DataAsset):
- MinMoveMult, MaxMoveMult
- MinCDMult, MaxCDMult (example: 0.25..4.0)

Cooldown scaling must be implemented centrally (MMC or a single shared function), not per ability.

---

## 6) Energy rules (v1)
- Basics generate energy on cast (and optionally on hit) via designer-authored values.
- Ultimate casts when Energy >= MaxEnergy (default behavior).
- Exact energy gain values are authored in AbilityData/GE, but the trigger rule is centralized.
